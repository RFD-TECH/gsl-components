# Migration guide: update to latest (Agent Instructions)

Agent-only. Every breaking change and deprecation between `1.22.0` and the latest release,
organised as directives. There is one upgrade path, whatever version you are coming from: install
the latest, run the codemod, then work through the short list of things it is not entitled to
decide. See [Changelog](/docs/changelog) for the dated list.

## Upgrading: run the codemod

Everything mechanical in this upgrade is done by `rfdui migrate`. It parses your JSX with the
TypeScript compiler resolved from your own app, so multi-line props, aliased imports
(`AppHeaderProfile as Profile`) and your own same-named components are all handled correctly: and
anything needing a judgement call is reported with a file and line rather than guessed at.

```bash
npm install @rfdtech/components@latest  # or pnpm add / yarn add

npx rfdui migrate                      # dry run: prints every change it would make
npx rfdui migrate --write              # apply
npx rfdui migrate --preserve --write   # apply, but pin the pre-2.3 appearance
npx rfdui migrate --path apps/web      # limit to one directory or file
```

It never writes without `--write`, and it never touches CSS.

In a pnpm workspace where the root does not itself depend on `@rfdtech/components`, `npx` cannot
see the local binary and goes looking on the registry. Run `pnpm exec rfdui migrate` from the
package that does depend on it.

### What it rewrites

| # | Change | Rewrite |
|---|--------|---------|
| 1 | `AppHeaderProfile` is a deprecated wrapper | Renamed to `ProfilePopover`, at the import, both JSX tags, and every reference |
| 1 | Its callbacks moved onto the built-in rows | `onProfileClick` → `onMyProfile`, `onSettingsClick` → `onAccountSettings`, `onHelpClick` → `onHelpAndSupport` |
| 1 | `headerAction` no longer does anything | Removed. The popover header shows a built-in theme toggle whenever a `ThemeProvider` is in the tree |
| 9 | `gslTheme()` → `cletTheme()` | Renamed, along with every `Gsl*` type alias (`GslThemeConfig`, `GslColorValue`, …) |
| — | The 2.3 layout shell | `AppHeader` unset/`"default"` → `"plain"`, `Sidebar variant="plain"` → `"primary"`, and a redundant `AppLayout variant="default"` dropped |

With `--preserve` the last row inverts: `AppLayout` is pinned to `variant="panel"` and
`AppHeader variant="plain"` becomes `variant="primary"`, so the app keeps its current appearance
and only the renames land.

Two behaviour changes ride along with the `ProfilePopover` rename and are reported when it happens:
sign-out now opens a "Confirm Sign Out" dialog first (pass `noConfirmSignOut` for the old
fire-immediately behaviour), and `items` now defaults to the three standard rows: only pass an
`items` array when the system genuinely needs different ones, since it replaces the defaults rather
than merging with them.

### What it reports instead of rewriting

Each of these needs a decision about data or intent that a codemod isn't entitled to make. The run
prints the file and line for every one.

**§2, §3, §6: `AppSwitcher`.** Deprecated in favour of `Launchpad`, and not a drop-in replacement.
`maxItems` now defaults to 6, so an `AppSwitcher` you keep needs `maxItems={apps.length}` if it
shows more. Moving to `Launchpad` means re-authoring the app list: icons become
`SystemLaunchpadIcon` or `LaunchpadIconTile` (a raw image URL is no longer accepted), the grid is a
fixed 3×3 with an expand modal, and there is no `maxItems`, `columns`, or generic `footer` slot ,
`children` takes a single optional `RoleSelect`. Stay on `AppSwitcher` only if you genuinely need a
flexible column count, an uncapped grid, or a custom footer.

**§4: `TableContent` with `selectable` and no `rowActions`.** The empty kebab column is gone. If
you relied on its Select/Deselect entry, add an explicit row action.

**§5: brand tokens.** Defaults moved from red to navy (`--clet-primary`), gained gold
(`--clet-secondary`), and switched typography to Roboto Serif and Lato. Keeping the new defaults
needs no work. If the project already overrides `--clet-*` tokens, list every override of a *known*
token: a `cletTheme()` call, or CSS setting a real `--clet-*` property, cross-checked against
`get_tokens()`: and ask about each one individually. Some are deliberate brand choices; others
only ever existed to match the old pre-rebrand defaults and should go now that those defaults
changed. Don't decide silently and don't batch it into one yes/no. Overrides belong in
`src/clet.theme.ts` (see [Theme](/docs/theme#recommended-file-srcclettheme-ts)), side-effect
imported once from your entry point.

**§7: `CountrySelector`.** Deprecated, still works. For a standalone picker use `Combobox` with
`options` built as `{ value: code, label: name }`; for phone entry use `PhoneNumberInput`'s built-in
picker rather than pairing a separate selector with a text input. `Combobox` has no built-in flag
rendering: pass one as each option's `icon` (e.g. from `country-flag-icons/react/3x2`) if needed.

**§8: `NetworkOperator`.** Deprecated, still works. Replace with `Combobox`, mapping each option's
`image` to the option's `icon` as an `<img>`.

**§9: `.gsl-*` class names in your own CSS and `className` strings.** Left alone on purpose. Every
rendered element carries both classes (`class="clet-sidebar gsl-sidebar"`), every internal token
read resolves as `var(--gsl-x, var(--clet-x))`, and `ThemeProvider` sets both `data-clet-theme` and
`data-gsl-theme`. This is a permanent compatibility alias with no removal date, so existing
selectors keep matching: and a blind `gsl-` → `clet-` rewrite would also rename any class of your
own that happens to start with `gsl-`. Prefer the `clet-*` spelling in new code.

### Validate the run

The codemod's job is to change names, not behaviour. After `--write`:

1. Read `git diff`: the run prints one line per edit, and the diff should contain nothing else.
2. `npm run typecheck && npm run lint && npm run test`: a rename that missed a reference shows up
   here immediately.
3. Work through the reported items above; each names a file and line.
4. Open the app and compare against the previous build. Adopting the shell is a deliberate visual
   change (the brand colour moves from the header to the rail); anything else that moved is a bug
   worth reporting, not something to patch around.

### Removals the codemod does not cover

A removed component has no mechanical replacement to rewrite to, so these are hand edits. The
compiler finds all of them: after the upgrade, a typecheck lists every site.

**2.3: `LogoLoader` is gone**, with its tokens and its docs page. There is no branded loader in the
kit any more. Wherever one covered a gap, use the loading state of the component that owns the
region (`TableContent`, `MetricCard`, `Launchpad`, `ProfilePopover`, `SidebarLink`), which keeps
the layout stable and knows what the finished content looks like. A whole-route or app-boot loader
is the app's own to supply.

**2.3: `Card` lost `loading`, `loadingLabel` and `loadingMinHeight`.** A card no longer swaps its
children for a loader. Move the loading state inside:

```tsx
// before
<Card bordered loading={isLoading} loadingLabel="Loading members…" loadingMinHeight={420}>
  <Table>…</Table>
</Card>

// after
<Card bordered>
  <Table>
    <TableContent loading={isLoading} loadingRows={10} columns={columns} data={rows} />
  </Table>
</Card>
```

**2.3: every `TableFilter` field needs a `name`, and needs seeding from the URL.** A filter field
reaches the table's state only through the named form control it renders, so a field without a
`name` holds its own value, filters nothing and is left behind by "clear". Both requirements are
checked in development and reported to the console with the field and the fix:

```tsx
const { filters } = useTableState({ paramPrefix: "members" });
const [status, setStatus] = useState(filters.status ?? "");

<TableFilter variant="spread">
  <Combobox name="status" value={status || null} onValueChange={(v) => setStatus(v ?? "")} … />
</TableFilter>;
```

## Adopting the new design system

The codemod above is about not breaking on version bump. This section is about looking like the new design system: none of it is required for existing screens to compile, all of it is required for new or touched screens.

### Layout shell: `AppLayout` (default) + `Sidebar variant="primary"` + `AppHeader variant="plain"`

Adopt as a set, not individually:

```diff
-<AppLayout variant="stacked">
-  <AppHeader variant="plain">...</AppHeader>
+<AppLayout>
+  <AppHeader variant="plain">...</AppHeader>
   <AppSidebar>
-    <SidebarOverlay />
-    <Sidebar variant="plain">
+    <Sidebar variant="primary">
       ...
     </Sidebar>
   </AppSidebar>
   <AppBody><Outlet /></AppBody>
 </AppLayout>
```

- **`AppLayout` with no `variant`**: the rail runs the full height against the viewport edge and the header spans the content column only. Nothing is inset or rounded.
- **`Sidebar variant="primary"`**: the brand rail, `--clet-primary-surface` background, on-primary text, flush edges, uppercase group labels.
- **`AppHeader variant="plain"`**: square corners, the page surface, ordinary text, one hairline underneath.

#### Two renames you have to know about

**`AppLayout variant="default"` changed meaning.** It used to be the inset rounded-panel arrangement; that is now `variant="panel"`. Any `<AppLayout>` with no variant, or an explicit `variant="default"`, moves to the new flush shell on upgrade. Pass `variant="panel"` to keep the old look.

**`AppHeader variant="plain"` changed meaning.** It used to be the brand-coloured bar; that is now `variant="primary"`. An existing `variant="plain"` header turns from navy to the page surface on upgrade: which is the point of the change, but pass `variant="primary"` if you want the bar to stay coloured.

`variant="stacked"` is untouched, and remains a first-class arrangement for systems that want one full-width bar across the top. It pairs with `AppHeader variant="primary"`.

[`rfdui migrate`](#upgrading-run-the-codemod) moves all three across an app. Both modes leave `variant="stacked"` alone, and a `<Sidebar>` with no variant is reported rather than rewritten, because the panel-surface sidebar only becomes the brand rail if its layout went flush too.

**`<SidebarOverlay />` is now optional and rendered internally by `Sidebar` on mobile.** The old default shell required you to remember to drop `<SidebarOverlay />` into `<AppSidebar>` — forgetting it left the drawer with no backdrop. `Sidebar` now renders its own mobile overlay as a sibling of the `<aside>` (still null on desktop), so a missing explicit `<SidebarOverlay />` is harmless. If you do render one, two overlays stack — both close the drawer on click, no visual artifact — so existing code keeps working unchanged.

**`SidebarGroup collapsible`:** All nav groups use accordion sections, not flat lists. Initialize with `Main` group expanded, others collapsed.

**`SidebarFooter` is never omitted, and the identity block appears once:** either the header's `ProfilePopover` is `variant="full"` (avatar, name, role) and the footer holds the organisation wordmark, or the footer hosts a `ProfilePopover` in `fullName`/`email` mode and the header's drops to `variant="avatar"`. The shell's default is the first. Repeating name and role in both places is the thing to avoid.

**No `SidebarTrigger`:** The old panel layout shell renders `<SidebarTrigger>Menu</SidebarTrigger>` to manually toggle the sidebar. The shell drops it entirely, don't render `SidebarTrigger` in new/touched layouts; `AppHeader` already collapses to a hamburger below the mobile breakpoint and that button opens the drawer. `SidebarCollapse` is a different control, the desktop rail's collapse-to-icons toggle, and it does belong in the rail's `SidebarHeader`.

**`SidebarBadge` — numeric counts only, not decorative text:** Compose it inside a `SidebarLink`'s children (`{link.badge && <SidebarBadge>{link.badge}</SidebarBadge>}`). Reserve it for a live count of actionable items on that nav destination (e.g. `8` unread alerts) — the number should reflect real pending/important items, not a static placeholder. The one exception is a short text badge like `"New"` for a feature callout (e.g. on a newly-added "Documentation" link) — don't invent other text badges beyond that pattern.

**Branding moves out of the header and onto the rail.** On the shell, the brand sits in a `SidebarHeader` at the top of the primary `Sidebar`, with the collapse toggle beside it, and the header carries a search field instead:

```tsx
<AppHeader variant="plain">
  <AppHeaderSearch placeholder="Search" />
  <AppHeaderActions>...</AppHeaderActions>
</AppHeader>

<Sidebar variant="primary">
  <SidebarHeader>
    <SidebarBrand>
      <img src="/clet-logo.png" alt="" width={28} height={28} />
      <span className="clet-sidebar__header-title">YOUR PORTAL</span>
    </SidebarBrand>
    <SidebarCollapse />
  </SidebarHeader>
  <SidebarContent>...</SidebarContent>
  <SidebarFooter>...</SidebarFooter>
</Sidebar>
```

The rail's `SidebarHeader` is what the mobile drawer shows, so no `mobileHeader` prop is needed here: the same logo must not appear twice on screen, and with the brand on the rail the header has none to duplicate.

The reverse applies to `AppHeader variant="primary"` (the full-width brand bar, usually with `AppLayout variant="stacked"`): keep branding in the header via `AppHeaderBranding` (`logo`/`title`/`subtitle`), leave the sidebar without a `SidebarHeader`, and mirror the brand into the mobile drawer with the sidebar's `mobileHeader` prop, which the library wraps in a mobile-only `SidebarHeader`:

```tsx
<Sidebar
  variant="plain"
  mobileHeader={
    <SidebarBrand>
      <img src="/clet-logo.png" alt="" width={28} height={28} />
      <span>YOUR PORTAL</span>
    </SidebarBrand>
  }
>
  <SidebarContent>...</SidebarContent>
  <SidebarFooter>...</SidebarFooter>
</Sidebar>
```

- The `mobileHeader` prop only renders when `Sidebar variant` is `"plain"` or `"primary"` and the consumer hasn't already supplied their own `<SidebarHeader>` child: add your own `<SidebarHeader>` to fully own the header content, which is what the primary rail does.
- The `clet-sidebar__header--mobile-only` class is now a built-in library class. No consumer CSS is required — the library hides it on desktop via the existing `@media (width >= 769px)` block in `src/components/sidebar/styles/sidebar.css`. The older migration recipe that required a hand-written `@media` rule no longer applies.
- The `AppLayout` does **not** auto-extract the `AppHeaderBranding` and forward it to the sidebar. The two brand blocks (`AppHeaderBranding` for the header, `SidebarBrand` for the mobile drawer) are intentionally separate — they live in different visual contexts with different styling. Compose both, with the same logo/title content.

**Use the current brand logo (`clet-logo.png`) for any new system** — `gsl-logo.png` is the older mark used only by the legacy default layout shell (`DemoLayout`); don't reuse it for new work.

### Use built-in `loading` states — never hand-roll placeholders

Every component below supports a real `loading` prop with shimmering skeleton. Use it. Never render `"..."` placeholders, hand-rolled `<Spinner />`, or omit-until-ready.

| Component | Loading prop | Replaces |
| ----------- | ------------- | ---------- |
| `Launchpad` / `AppSwitcher` | `loading` | Disabled/empty trigger or nothing until apps arrive |
| `AppHeaderNotifications` | `loading` | Empty popover or hand-rolled spinner |
| `ProfilePopover` | `loading` + `loadingLabel` | `"..."` or nothing for name/email/avatar |
| `SidebarLink` | `loading` + `loadingLabel` | Not rendering nav items until data resolves, or full-page spinner |
| `MetricCard` | `loading` + `loadingLabel` | `"..."` or `"N/A"` in `value`/`description` |
| `TableContent` | `loading` + `loadingRows` | Empty table, spinner overlay, or hide-until-ready |

**SidebarLink pattern:**

```tsx
{navLoading ? (
  <SidebarGroup>
    {Array.from({ length: 6 }).map((_, i) => (
      <SidebarLink key={i} loading icon={<span />}>Loading</SidebarLink>
    ))}
  </SidebarGroup>
) : (
  navGroups.map((group) => /* real nav */)
)}
```

### One role switcher, consistent across all three locations

`RoleSelect` is required `children` on `Launchpad`, and accepted `children` on `ProfilePopover` (header) and `ProfilePopover` (sidebar footer). **Whenever a system allows a user to have more than one role — true for most systems — wire the same `RoleSelect` state into all three: `Launchpad`, the header `ProfilePopover`, and the sidebar footer `ProfilePopover`.** Don't add it to only one or two.

```tsx
const [selectedRole, setSelectedRole] = useState(roles[0].id);
const roleSelectProps = { title: "View as", roles, selectedRole, onClickRole: (r) => setSelectedRole(r.id) };

// Header
<ProfilePopover variant="avatar" user={user} onSignOut={onSignOut}>
  <RoleSelect {...roleSelectProps} />
</ProfilePopover>

// Sidebar footer
<SidebarFooter>
  <ProfilePopover fullName={user.name} email={user.email} onSignOut={onSignOut}>
    <RoleSelect {...roleSelectProps} />
  </ProfilePopover>
</SidebarFooter>

// Launchpad — RoleSelect is required here, not optional
<Launchpad apps={apps} onAppSelect={onAppSelect}>
  <RoleSelect {...roleSelectProps} />
</Launchpad>
```

Neither `ProfilePopover` above passes `items` — both render the default "My Profile"/"Account Settings"/"Help and Support" rows. Only add `items` if the system needs different rows.

**Header `ProfilePopover` uses `variant="avatar"` when sidebar footer popover exists.** Reserve `variant="full"` for headers with NO sidebar footer.

### Table family — adopt together

| Component | Prefer | Over |
| ----------- | -------- | ------ |
| `TableContent` | `variant="panel"` | `"default"` |
| `TableFilter` | `variant="spread"`, up to two fields | `"popover"` (default) |
| `TableFooter` | `noBorder` | default top border |

`variant="spread"` is honoured for one or two fields. A `TableFilter` holding a third groups itself
back into the popover, whatever the markup asks for, and says so once in the dev console: three
controls laid out inline stop reading as a filter row and start competing with the search field
next to them. The fields, their names, their URL keys and "clear" are identical in both variants,
so nothing but the presentation moves, and screens already carrying four spread filters quietly
become a single Filters trigger on upgrade.

```diff
 <Table paramPrefix="members">
   <TableHeader>
     <TableSearch placeholder="Search members..." />
-    <TableFilter>
+    <TableFilter variant="spread">
       <Dropdown name="role" ... />
     </TableFilter>
   </TableHeader>
-  <TableContent variant="panel" columns={columns} data={data} rowKey={...} />
+  <TableContent variant="panel" columns={columns} data={data} rowKey={...} />
-  <TableFooter>
+  <TableFooter noBorder>
     <TablePagination ... />
   </TableFooter>
 </Table>
```

`noBorder` is a real `TableFooterProps` prop (applies `.clet-table__footer--no-border { border-top: none; }` internally), not a demo hack. Older code passing `className="clet-table__footer--no-border"` by hand still works — prefer `noBorder` in new/touched code.

### Other preferred variants

| Component | Prefer | Over |
|-----------|--------|------|
| `MetricCard` | `variant="outline"` | `"default"` |
| `Tabs` | `variant="pill"` | `"default"` |

Use `SectionHeader` (with `SectionTitle`/`SectionDescription`/`SectionActions`) for page headers — never hand-rolled `<div>`s.

## PageSection — consistent section spacing

Every distinct content section on a page must be wrapped in `<PageSection>` instead of a
hand-rolled `<div>` with margin:

```diff
-<div style={{ marginBottom: 24 }}>
+<PageSection>
   <MetricCard variant="outline" ... />
-</div>
+</PageSection>
```

`PageSection` applies `gap: var(--clet-app-layout-body-gap)` — no new token, no hardcoded
value. All sections get uniform spacing automatically.

## QuickActions — dashboard action grids

Use `<QuickActions>` for quick-action grids on dashboards. It replaces any hand-rolled
"action buttons" row with a responsive tile grid (1/2/3 columns) and an optional "Customize"
dialog for toggling visibility:

```diff
-<div className="flex gap-4">
-  <Button>Add Member</Button>
-  <Button variant="secondary">Export</Button>
-</div>
+<QuickActions
+  actions={[
+    { id: "add", label: "Add Member", icon: <UserPlus size={18} />, onClick: ... },
+    { id: "export", label: "Export Data", icon: <Download size={18} />, onClick: ... },
+  ]}
+  customizable
+/>
```

The customize feature is fully controlled — pass `hiddenIds` and `onToggleVisibility` to
manage which actions are visible. Persist the state however you like (localStorage, zustand,
etc.).

All variants above are additive — no deadline to migrate old screens. But any screen built fresh or substantially touched must use these variants.

## Checklist

**Compatibility (keeps existing screens compiling):**

- [ ] Install the latest release, then run `npx rfdui migrate` and read the dry run, then `--write` (or `--preserve --write` to keep the current look)
- [ ] Confirm the run: `git diff` shows only what it printed, and typecheck, lint and tests pass
- [ ] Work through everything under "What it reports instead of rewriting": each names a file and line
- [ ] Replace every `LogoLoader` and every `<Card loading>` by hand ("Removals the codemod does not cover"); typecheck lists them
- [ ] Give every `TableFilter` field a `name` and seed it from `useTableState().filters`; the dev console reports any that are missed
- [ ] Convert every `AppSwitcher` → `Launchpad` when possible (§6) — `AppSwitcher` is deprecated
- [ ] Pass `maxItems={apps.length}` to any `AppSwitcher` you keep with >6 apps (§3)
- [ ] Add explicit `rowActions` Select/Deselect to `selectable`-only tables that need it (§4)
- [ ] If the project already has `--clet-*` token overrides, list every known-token override found and ask the user per-token whether to keep it or adopt the new default — never decide silently (§5)

**Design system adoption (the actual "looks like v2" bar — for new/touched screens):**

- [ ] New `AppSwitcher`-like work uses `Launchpad` first (§6) — `AppSwitcher` is deprecated, no new features
- [ ] New/rebuilt layout shells use `AppLayout` (no variant) + `Sidebar variant="primary"` + `AppHeader variant="plain"` + collapsible `SidebarGroup`s together ("Layout shell")
- [ ] Every layout has a `SidebarFooter`, with the identity block in exactly one place: a `variant="full"` header popover plus a footer wordmark, or a footer popover plus a `variant="avatar"` header ("Layout shell")
- [ ] No `SidebarTrigger` in new layouts: that's an old panel-shell-only pattern. `SidebarCollapse` in the rail's `SidebarHeader` is a different control and does belong ("Layout shell")
- [ ] `<SidebarOverlay />` is no longer required — `Sidebar` renders its own mobile overlay internally ("Layout shell")
- [ ] `SidebarBadge` shows a real numeric count of actionable items, not decorative text (`"New"` is the one exception) ("Layout shell")
- [ ] Branding at the top of the rail in a `SidebarHeader`, using the current logo (`clet-logo.png`), never duplicated in the header: which carries an `AppHeaderSearch` instead. On a `variant="primary"` header it is the other way round: `AppHeaderBranding` in the header, and the same brand passed as the sidebar's `mobileHeader` ("Layout shell")
- [ ] Every loading-props table component uses its real `loading` prop — never hand-rolled `"..."` or spinner ("Use built-in loading states")
- [ ] `RoleSelect` wired from the same state everywhere it appears (`Launchpad`, header `ProfilePopover`, sidebar footer `ProfilePopover`), whenever the system allows more than one role ("One role switcher")
- [ ] Header `ProfilePopover` uses `variant="avatar"` when a sidebar footer popover exists, and `variant="full"` when it doesn't ("One role switcher")
- [ ] Neither `ProfilePopover` passes a custom `items` array unless the system needs rows other than the built-in "My Profile"/"Account Settings"/"Help and Support" defaults ("One role switcher")
- [ ] New/touched `Table`s use all three: `TableContent variant="panel"`, `TableFilter variant="spread"`, `TableFooter noBorder`
- [ ] `MetricCard variant="outline"`, `Tabs variant="pill"` on new usage
- [ ] New page headers use `SectionHeader`/`SectionTitle`/`SectionDescription`/`SectionActions`
- [ ] Every page section is wrapped in `<PageSection>` — no bare `<div>`s with margin ("PageSection")
- [ ] Quick-action rows use `<QuickActions>` with customizable visibility ("QuickActions")
- [ ] `Launchpad`'s expand button shows its icon always, its "See more" label only once `apps.length` exceeds 9 — never the old bordered "See all" button
